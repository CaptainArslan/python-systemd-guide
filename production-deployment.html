09

Architecture & what you'll need

Part 1 got one Python process running in the background. Production adds two more pieces in front of it: a process manager that's actually resilient, and a reverse proxy that gives you a real domain and HTTPS instead of a bare port.

request path
Browser
↓ https://myapp.example.com
Nginx (ports 80 / 443)
↓ proxy_pass → 127.0.0.1:8000
Gunicorn + Uvicorn workers, managed by systemd
↓
Your app (api.py → core logic)

Only ports 80, 443, and 22 need to be public. Port 8000 stays private — never open it in a firewall, and don't leave it exposed on a temporary port like 8080 for a "final" deployment.

Deployment values used throughout this guide:

reference
Linux user             ubuntu
Project directory      /var/www/myapp
Virtual environment    /var/www/myapp/venv
ASGI entry point       api:app
Internal address       127.0.0.1:8000
systemd service        myapp.service
Public domain          myapp.example.com

Install server packages

shell
sudo apt update
sudo apt install -y git nginx python3 python3-pip python3-venv python3-dev build-essential snapd

Verify:

shell
python3 --version
git --version
nginx -v

snapd is only needed later, for Certbot in step 21 — installing it now saves a trip back.

11

Set up Git deploy access

If your repo is private, the server needs its own key so it can pull code without your personal credentials. Generate it as whichever user will own the deployment:

shell
ssh-keygen -t ed25519 -C "myapp-deploy-key" -f ~/.ssh/id_ed25519          # no passphrase — this runs unattended
cat ~/.ssh/id_ed25519.pub

Add the printed public key to your Git host as a read-only deploy key (on GitHub: Repository → Settings → Deploy keys → Add deploy key). The server only needs to pull, never push.

shell
ssh -T git@github.com          # confirms the key works

Never copy or expose ~/.ssh/id_ed25519 (no .pub) — that's the private half.

13

Create the venv & install dependencies

shell
cd /var/www/myapp
python3 -m venv venv
./venv/bin/python -m pip install --upgrade pip setuptools wheel
./venv/bin/python -m pip install -r requirements.txt

If the project doesn't already serve HTTP, add a production API stack:

shell
./venv/bin/python -m pip install fastapi gunicorn "uvicorn[standard]" uvicorn-worker

Add the same four packages to requirements.txt so the next deploy reproduces this environment exactly. Note the worker class: the maintained path is uvicorn_worker.UvicornWorker (from the separate uvicorn-worker package) — not the older uvicorn.workers.UvicornWorker. If you used the old path in Part 1, it's worth switching.

14

Wrap the app for the web

Running main.py from the shell proves your logic works, but it doesn't make it reachable from a browser. Keep main.py as-is and add a thin api.py next to it that imports the same functions and exposes them over HTTP:

shell
./venv/bin/python main.py --help          # confirm the existing CLI still works first
api.py
#!/usr/bin/env python3

import logging
import os
from datetime import date

from fastapi import FastAPI, HTTPException, Query

from core.logic import run_job


logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s",
)
logger = logging.getLogger(__name__)

app = FastAPI(
    title="My App API",
    description="Web interface for the existing core logic",
    version="1.0.0",
)


@app.get("/")
def home():
    return {"success": True, "message": "My App is running"}


@app.get("/health")
def health():
    return {
        "status": "healthy",
        "service": "myapp",
        "third_party_configured": bool(os.getenv("THIRD_PARTY_API_KEY")),
    }


@app.post("/api/jobs")
def create_job(
    job_date: str = Query(default_factory=lambda: str(date.today())),
    target_id: str | None = Query(default=None),
):
    try:
        logger.info("Running job: date=%s target=%s", job_date, target_id or "all")
        result = run_job(date_str=job_date, single_target_id=target_id)
        return {"success": True, "data": result}
    except Exception as exception:
        logger.exception("Job failed")
        raise HTTPException(status_code=500, detail="Job failed") from exception

The /health endpoint matters more than it looks — step 16 onward all use it to prove each layer (app, systemd, Nginx, HTTPS) is actually working.

15

Create the production .env file

shell
nano /var/www/myapp/.env
.env
THIRD_PARTY_API_KEY=replace-with-the-real-key
PYTHONUNBUFFERED=1

systemd's EnvironmentFile only understands plain KEY=value lines — no export, no quotes-as-shell-syntax, no expressions.

shell
sudo chown $(whoami):www-data /var/www/myapp/.env
sudo chmod 640 /var/www/myapp/.env

sudo mkdir -p /var/www/myapp/output
sudo chown -R $(whoami):www-data /var/www/myapp/output
sudo chmod 775 /var/www/myapp/output
16

Smoke-test with Gunicorn

Before wiring up systemd, prove the production server itself starts cleanly, in the foreground:

shell
cd /var/www/myapp

set -a; source .env; set +a

./venv/bin/gunicorn api:app \
  --workers 2 --worker-class uvicorn_worker.UvicornWorker \
  --bind 127.0.0.1:8000 \
  --access-logfile - --error-logfile -

From another terminal:

shell
curl -i http://127.0.0.1:8000/health          # expect HTTP/1.1 200 OK

Stop it with Ctrl+C before moving on — systemd will own the process from here.

17

Create the production systemd service

This builds on the unit file from Part 1, with a few production upgrades: it runs as your deploy user rather than www-data (so it can write generated files), restarts only on-failure, and gives systemd explicit start/stop timeouts.

shell
sudo nano /etc/systemd/system/myapp.service
myapp.service
[Unit]
Description=My App (Gunicorn + Uvicorn workers)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=ubuntu
Group=www-data
WorkingDirectory=/var/www/myapp

EnvironmentFile=/var/www/myapp/.env
Environment=PYTHONUNBUFFERED=1
Environment=PYTHONPATH=/var/www/myapp

ExecStart=/var/www/myapp/venv/bin/gunicorn api:app --workers 2 --worker-class uvicorn_worker.UvicornWorker --bind 127.0.0.1:8000 --access-logfile - --error-logfile - --timeout 300

Restart=on-failure
RestartSec=5
TimeoutStartSec=30
TimeoutStopSec=30
KillSignal=SIGTERM

StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target

Swap User=ubuntu for whichever account owns /var/www/myapp. Running the service as www-data is possible, but only after deliberately granting it write access everywhere the app needs it.

shell
sudo systemctl daemon-reload
sudo systemctl enable myapp.service
sudo systemctl start myapp.service

Verify:

shell
sudo systemctl status myapp.service --no-pager
sudo ss -ltnp | grep ':8000'          # must show 127.0.0.1:8000, never 0.0.0.0:8000
curl -i http://127.0.0.1:8000/health
shell
sudo journalctl -u myapp.service --no-pager -n 100
sudo journalctl -u myapp.service -f
18

Point DNS at the server

DNS record
Type:  A
Name:  myapp
Value: SERVER_PUBLIC_IP
TTL:   300 or Auto
shell
dig +short myapp.example.com

Don't request a certificate in step 21 until this returns your server's real IP — Certbot needs DNS to resolve correctly first.

19

Configure Nginx as a reverse proxy

shell
sudo nano /etc/nginx/sites-available/myapp.example.com
myapp.example.com
server {
    listen 80;
    listen [::]:80;

    server_name myapp.example.com;

    access_log /var/log/nginx/myapp-access.log;
    error_log /var/log/nginx/myapp-error.log;

    client_max_body_size 20M;

    location = /nginx-health {
        access_log off;
        default_type text/plain;
        return 200 "nginx healthy\n";
    }

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 60s;
        proxy_send_timeout 300s;
        proxy_read_timeout 300s;
        proxy_buffering off;
    }
}

Don't add default_server here if another site on this machine already owns that role.

shell
sudo ln -sfn /etc/nginx/sites-available/myapp.example.com /etc/nginx/sites-enabled/myapp.example.com

sudo nginx -t          # only proceed if this passes
sudo systemctl reload nginx          # reload, not restart — don't drop other sites
shell
curl -i http://myapp.example.com/nginx-health
curl -i http://myapp.example.com/health
20

Lock down the firewall

shell
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw status numbered

Don't open port 8000 — Nginx reaches it locally, nothing else should. If you're on a cloud provider, also check its separate network firewall (AWS Security Groups, DigitalOcean Cloud Firewalls, etc.) — ufw alone won't help if that layer still allows the world in on 8000.

21

Enable HTTPS with Certbot

shell
sudo snap install core && sudo snap refresh core
sudo snap install --classic certbot
sudo ln -sfn /snap/bin/certbot /usr/bin/certbot

certbot --version
shell
sudo certbot --nginx -d myapp.example.com          # choose the HTTP → HTTPS redirect when asked
shell
sudo nginx -t
sudo systemctl reload nginx
curl -i https://myapp.example.com/health
shell
sudo certbot renew --dry-run          # confirms auto-renewal will actually work

Diagnostics

Test each layer in order — the first one that fails tells you where the problem actually is:

shell
# 1. Service state
sudo systemctl is-active myapp.service

# 2. Private app, direct
curl -i http://127.0.0.1:8000/health

# 3. Nginx syntax
sudo nginx -t

# 4. HTTP through the proxy
curl -i http://myapp.example.com/health

# 5. HTTPS through the proxy
curl -i https://myapp.example.com/health
failure → likely cause
status=200/CHDIR              WorkingDirectory doesn't exist or isn't accessible
Service keeps restarting      Gunicorn import, dependency, env, or permission error
Port 8000 refuses connections The app isn't running
Nginx returns 502              Nginx can't reach 127.0.0.1:8000
Wrong site loads on the domain DNS or server_name wrong, or site not enabled
HTTP works, HTTPS fails        Certificate or SSL config problem
Local works, external fails    Cloud security group, ufw, DNS, or public-IP issue
shell
sudo journalctl -u myapp.service --no-pager -n 100
sudo tail -100 /var/log/nginx/myapp-error.log
sudo tail -100 /var/log/nginx/myapp-access.log

Security checklist

checklist
• Keep Gunicorn bound to 127.0.0.1:8000, never 0.0.0.0:8000
• Don't open port 8000 in ufw or your cloud security group
• Keep .env out of git; mode 640 or tighter
• Add authentication before exposing real operations publicly
• Consider protecting /docs and /openapi.json outside staging
• Don't add a second default_server if one already exists
• Always run "nginx -t" before every "systemctl reload nginx"
